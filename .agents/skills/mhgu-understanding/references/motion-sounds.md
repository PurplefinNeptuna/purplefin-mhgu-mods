# Motion sound sequences (MSS)

## Motion sound sequences (MSS)

Read from the 1.4.0 main (decompiled with the playbook's export, checked in `research dis`) and `sound\call\pl\pl_cmn` in `player/com/com.arc`.

- `rFestaSoundSequence` (DTI id `0x10ebe843`, vft `0x1769690`) is the `MSS` file: `sound\call\pl\pl_cmn` (player common, 330 motions) and `sound\call\pl\pl_wpNN` (one per weapon, in `player/quest/wNN.arc`). Its load (slot 0x2c, `0x4d9bec`) checks magic `0x53534d` and version `0x20131015`, copies the file to resource +0x64 and sets +0x68 = file + 0x10 and +0x6c = file + 0x410.
- File: +8 u16 record count, +0xb byte the file's type (`pl_cmn` 2), +0x10 512 u16 motion index (`0xffff` none), +0x410 records {u32 motion, u32 offset}. A sequence: +0 u32 motion, +4 u16 key count, +0xc offset of its start block, keys {u32, u32 offset} from +0x10 (`0x4d9e40`). A key: u16 frame, u16 event count, u32 event offsets from +4, each relative to the key (`0x4d9e68`). An event: u8 opcode, u8 kind (1 a sound command), u8 n, u8 flags (bit 0 skips it), then its arguments from +4 + n*4. Lookups: `0x4d9dbc(resource, motion)` (linear, on the sequence's own motion word), `0x4d9e20` the start block.
- `cFestaSoundSequence` (vft `0x17694d8`, 572 bytes) plays them for an owner at +0x164 with up to eight channels (count +8), one per motion layer: layer motion u16 at owner + 0x4b4 + layer*0x140 (high byte the bank), read as bank*1000 + index, and frame f32 at +0x500. Five resource slots at +0x150 (slot 4 for a motion 15000 and up). Per channel: +0x10 motion, +0x30 slot, +0xd0 key index, +0xf0 sequence, +0x130 key. The update is slot 0x18, `0x4d5e90`; it runs each key passed this frame through `0x4d65bc(sequence, channel)`, which calls the event executor for each event.
- Event executor `0x4d74f8(channel, sequence, event)` (callers `0x4d6624`, `0x4d6700`; entry `cmp r1,#0; cmpne r2,#0; beq`, no PC-relative loads). Argument readers: `0x4d7524`/`0x4d7538` u8, `0x4d754c` u16, `0x4d7560` s8, `0x4d7574` s16, `0x4d7588` u32. An opcode runs only when the file's type matches: 1 takes 0x40, 0x5e, 99; 2 takes 0x64..0x6a; 6 takes 0x79..0x7f, 0x82; 7 takes 0x80, 0x81, 0x84, 0x86; 0x83 and 0x85 check no type. Opcode 0x66 reads u16 bank, u16 request, s16 attach, u16, u8 random flag, u8 threshold, u16 alternative request, u8, and plays `0x4f0be8(system, owner, request, attach, u16, 4, bank)`. 0x64 and 0x6a also play through `0x4f0be8` with type 0, 0x65 type 1, 0x67 type 9, 0x68 type 5 (or `0x4f0700` when sequence +0x1aa is set). Every opcode takes the system from the same GOT cell (`0x1838be8`). In `pl_cmn`: 0x64 1071 events, 0x69 744, 0x68 540, 0x67 474, 0x65 151, 0x66 85.
- `0x4f0be8` has two direct callers, both in this code: the executor and `0x4d63b8`, the flush of the sequence's queued requests (+0x1ac, four of 0x20 bytes), which switches on owner byte +0x1052 (0, 6, 7 `0x4f0be8`; 1 `0x4f1974`; 2 `0x4f1c0c`; 4 `0x4f1ee4`).
- Gather motions seen: 2005 and 2019 (common file), 202 (carve) and 206 (weapon file); the item-get sound is not among their events (Jingles, above).
