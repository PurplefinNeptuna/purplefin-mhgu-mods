# Sounds and jingles

Static reading of the 1.4.0 main and RomFS, plus the MHGU Recomp runs named.
Source: `work/wishfinder/NOTICES.md`; decoded samples in
`work/wishfinder/sound-samples/`.

## Playing a menu sound

`0x54f260(kind, id)` picks one of the sound-manager calls by kind: 0 `0x4eeb78` with an id, 1 `0x4eec94`, 4 `0x4ef2c4`, 6 `0x4eed04` (bank 0..6 in all). The native cursor `0x54ee98` calls the kind functions directly. Bank 0 ids the game uses most: 2 (356 sites), 1, 6, 3, 13, 4, 14, 7, 10, 16, 31, 9, 15, 21, 27, 30; bank 1 uses ids 101..194.

The smithy uses `0x54f260(0, n)` with 1 accept, 2 cancel, 3 deny (heard in WishFinder). Which kind is cursor move and which page turn is unread. `0x54f260` passes n through unchanged and `0x4eeb78(sound, n)` queues it at slot +0x10 with bank `mpResSeSys` (+0xc0 of `sSoundControl`, DTI vft `0x17696a0`), so n is a `snd_sys_com` request id; Sound data gives how a request names a wave. The four heard cases agree: 1 `sys_kettei` (accept), 2 `sys_cancel`, 3 `sys_bubu` (deny), 5 `sys_info` (the popup). n = 43 (`sys_panel_slider`) was not heard in a quest (WishFinder's predecessor r40 called it once, from the pouch add, in the update the popup played `sys_info`); its wave is 0.31 s at a normal level, its record's +0x24 f32 is -6.0 (5: -3.5; 42: -2.3), and no record or bank field read so far (+0x44 nibble 4, the group, the key) differs from a request that plays, so why it was not heard is open until a run plays it alone.

## Sound data

- Menu sounds are `sound\se\system` in `loc/arc/resident.arc`: 36 waves (type `0x79c47b59`), bank `snd_sys_com` (SBKR, `0x15d782fb`) and request table `snd_sys_com` (SRQR, `0x1bcc4966`).
- **How a request names a wave** (bytes of the loaders and lookups, checked on every request of `snd_sys_com`, `snd_sys_lb`, `snd_jingle_qst` and the `rt_jNN` banks: each resolves to one wave). SRQR (`rSoundRequest`, vft `0x1794210`, load `0xb67a0c`): header +8 record count, records of 0x84 bytes from 0x34; `0xb68280(table, id)` finds a record by its u16 id at +0 through an index built at load (`0xb67cf0`). Record: byte +2 the key, s16 +0x1c the next request of a chain (-1 none), u16 +0x1e the bank group. SBKR (`rSoundBank`, vft `0x1789758`, load `0x87654c`): magic, version 4, +8 group count, +0xc wave count, +0x10 a third count; groups of 12 bytes from 0x14 (u32: u16 group id, wave count in bits 17..26; u32 first wave); then each wave as a null-terminated path and 80 bytes of parameters (in memory 84-byte records: +0 the wave resource, +4 the parameters). A wave answers a key when parameter bytes 0x4c <= key <= 0x4d (memory +0x50, +0x51; the picker `0x876ab0` compares them), within the request's group. Parsers: `work/wishfinder/sound-samples/sbkr.py` and `srqr_map.py ARC KEY` (prints every request, group, key and wave).
- `snd_sys_com` requests: 1 `sys_kettei`, 2 `sys_cancel`, 3 `sys_bubu`, 4 `sys_cursor`, 5 `sys_info`, 6 `sys_undermenu`, 7 `sys_undercursor`, 8 `sys_box_open`, 9 `sys_box_get`, 10 `sys_money`, 11 `sys_mix_success`, 12 `sys_mix_lost`, 13 `sys_saywindow`, 14 `sys_itemsort`, 15 `sys_manual_itemsort`, 16 `sys_itemidou`, 17 to 20 and 58 to 60 `sys_sine` (18 to 20 and 58 to 60 chain on), 21 `sys_item_suteru`, 24 `h_note_open`, 25 `h_note_put`, 26 `h_note_mekuru`, 27 `sys_undercursor`, 28 `sys_moji`, 29 `sys_next`, 30 `sys_quest_papu`, 31 `item_box_dasiire`, 32 `sys_saywindow_attention`, 33 `sys_saywindow_important`, 34 `sys_head_mark`, 41 `sys_panel_move`, 42 `sys_panel_set`, 43 `sys_panel_slider`, 44 `sys_panel_trash`, 45 `lb_sys_display_updown`, 161 and 171 `lb_sys_chat_reception`, 162 `lb_sys_checkmark_on`, 163 `lb_sys_checkmark_off`; 201 to 213 (groups 2 and 3) `sys_kettei`, `sys_cancel`, `sys_panel_set`, `sys_panel_move`, `sys_undercursor`, `sys_manual_itemsort`, `sys_cursor`, `sys_cursor`, `sys_undercursor`, `sys_cancel`, `sys_itemsort`, `sys_moji`, `sys_bubu`.
- `snd_sys_lb` (`loc/arc/village/common.arc` and `title.arc`; bank 1 ids 101..194, likely `mpResSeSysLb` +0xc4 through `0x4eec94`: inference) requests run from 101 `lb_sys_arm_change` to 300 `sys_quest_papu_rabbit_lb`; `srqr_map.py` lists them. The lobby jingle bank `<lang>\sound\se\jingle\lobby\snd_jingle_lb` (`village/common_<lang>.arc`; ids 1..6, 21, 22) has two groups and no waves in its SBKR (52 bytes) in every language, so those requests play nothing; no other archive holds `jingle\lobby` waves.
- Quest common sounds are `sound\se\com\wav` in `loc/arc/quest.arc` (148 waves).
- Waves are DSP-ADPCM, mono or stereo (byte 4 = channels; stereo interleaved in 0x100-byte blocks): +0x10 a build date, +0x18 16 LE s16 coefficients, +0x60 nibble count, +0x64 sample rate, data from +0x78 in 8-byte frames. `work/wishfinder/sound-samples/dsp2wav.py ARC PREFIX OUTDIR` decodes them.

## Jingles

- `sSoundControl` +0xc8 is `mpResSeJingle`. The pickup jingles are the realtime jingles, one per `arc/sound/rt_jNN.arc` (`sound\rt_j%02d`, built by `0x15339c`): 01 `item_non`, 02 `item_gets`, 03 `item_gets02`, 04 `katamari`, 05 `egg_get`, 06 `egg_lost`, 07 `mix`, 08 `fish_get`, 09 `trophy`, 10 `retire`. Stereo at 44.1 or 48 kHz.
- Three request functions queue a jingle in `sSoundControl`'s request slots (kind byte 2) on `mpResSeJingle`: `0x4eede8(sound, id, arg)` (one caller, the Alchemy barrel's result `0x2e115c` at `0x2e1340`: id = the barrel item index player +0x32e4 + 11, arg -2), `0x4eee68` (one caller, fixed id 1) and `0x4eef00(sound, kind)` (kind 0 -> id 2, 1 -> 3, 2/3/130/131 -> 4, 4 -> 5, else nothing). In a quest those ids are the quest jingle bank `<lang>\sound\se\jingle\quest\snd_jingle_qst` in `<lang>/arc/quest_<lang>.arc` (six waves; one group, keys 0..4 and 10): id 1 `normal_meet_bgm`, 2 `namaniku`, 3 `namayake`, 4 `jouzu`, 5 `koge`, 6 key 100 (no wave answers it), 11..15 `kizuna_success`. The `rt_jNN` names do not apply to these ids. The tester hears `jouzu` for a Well-done Steak (id 4). The village bank is `<lang>\sound\se\jingle\lobby\snd_jingle_lb` in `village/common_<lang>.arc`; which bank `mpResSeJingle` holds when is unread.
- **The gather jingle is a realtime jingle, `0x4ef090(sound, n)`** (`strb r1, [r0, #0xd5]; bx lr`, 13 callers). The hunter's get-item `0x2e04d4(player, item, ...)` adds through player slot 0x364 (the pouch add `0x19b7fc`, from `0x19c320`) and ends with `b 0x4ef090` with n 2 for a plain pickup (other branches below, "Which pickup gets which jingle"). The sound update's loader `0x4e9370` (state +0xd4) loads realtime jingle n (resource index 0x10414 + 532 + n, `0x1529a8`, then ready through `0x153078`) into +0xd0, keeps n at +0xd6, clears +0xd5, and queues request kind 3, id 1, bank +0xd0 inside the update, so the request table never shows it outside the update; the realtime slots do (`bank +0xd0`, word 1). In MHGU Recomp (WishFinder r139, `EVIDENCE.json` runtime_r139_recomp_2026_11_21) every gather of the run showed it two updates after its pouch add, and no supply box take did; the tester hears `item_gets` at a gather and `0x2e04d4`'s default n is 2, so n is the `rt_jNN` number (inference from that match, not heard for n 3). `sSoundControl` +0xd0 has no DTI name; +0xc0 `mpResSeSys`, +0xc4 `mpResSeSysLb`, +0xc8 `mpResSeJingle`, +0xd8 `mpResSeCom`, +0xdc `mpResSeMap`, +0xe0 `mpResSeTitle`, +0xe4 `mpResSeMonnyan`. Request slots: 64 of 36 bytes from +0xec (+0 used, +2 kind, +0x10 id, +0x14 word, +0x20 bank); realtime slots: 64 of 16 bytes from +0x9ec (+0 used, +4 resource, +8 request id, +0xc a handle, -2 when cleared; cleared at `0x4eb5fc`, walked at `0x4eb874`).
- `0x4eef00`'s callers (`0x2d55e0`, `0x2d5688`, `0x2d5734`, `0x2d5778`) are the end of the BBQ Spit (meat roasting), a switch on player +0x32d8, `| 0x80` for kind 2 when player byte +7 is clear. Each takes Raw Meat (45) through slot 0x360 and adds the result through slot 0x364. The kind comes from the roast timer f32 at +0x32d4 (`0x2d5488`), checked against the s16 table at `0x1628fb4` (360, 540, 40; the same row for item 44 and for the other spit): below 360 kind 0 (no item added, `namaniku`), 360 to 540 kind 1 Rare Steak (49, `namayake`), from 540 kind 2 Well-done Steak (50, `jouzu`), from 580 kind 4 Burnt Meat (51, `koge`). With skill 206 Outdoorsman ("Easier to fish and BBQ meat."), the well-done window is 530 to 590 (`vsel` at `0x2d541c`). Nothing in the function writes kind 3. The roast's start plays `0x4eee68` (id 1, `normal_meet_bgm`, the cooking tune; `0x2d5264`). So no BBQ result plays `item_gets02`.
- **Which pickup gets which jingle** (`0x2e04d4`, bytes). Arguments: player, item, amount, r3 flags (1 runs a quest check and `0x2e02d4`), stack word "fish" (0 from the gather wrapper, 1 from both fishing callers). Who calls it, and how gathering, mining, bugs, carving and fishing reach it: [Quest files](quest-files.md#gathering-areas-and-the-secret-area), "Pickups at runtime". Before the add, Honey (271), Royal Honey (2053) and the charms 353..356 can gain one: honey always with 244 Honey Hunter or 263 Soul of Yukumo; a charm on a roll below 30 of 100 with 245 Charm Chaser, 271 Crystalbeard Soul, 289 C.beard Soul X or 320 Pack Rat, else below 20 with 246 Charm Collector (skill ids: [Equipment and crafting](equipment-and-crafting.md), skill effects). The add's result codes and popups are in [Menus and screens](menus-and-screens.md#items-entering-the-pouch). Result 3 gives n 1 (`item_non`); on 5 the get-item queues hunter action 9999 (`0x2e9b7c(player, id, frames)`: the id at +0x2700, state +0x2754 = 3; ids from 1000 and from 2000 go through lookup tables, 9999 maps to 0) and plays n 1. Item 0 gives n 1 with no add. Otherwise, from the item record (`0x194228`; memory offsets, file layout in Equipment and crafting): a fish takes n 8 when +0xd (rarity, one below the shown value) is above 3, else 2; anything else takes n 4 when +0x1a is 2, else 2. After a successful add, an item in 2105..2115 (`0x1943bc`: the eggs, Sootstone, Quartz, Powderstone, Meteor Chunk, Eternal Fossil, Cannon Ammo) that the hunter now carries (`0x28813c`) sets the carry state and n 5. In 1.4.0's `table\itemData`, +0x1a is 2 only for Rustshard (357) and Ancient Shard (358). The fish with +0xd above 3 are Speartuna, Gastronome Tuna, Ancient Fish, Armored Bream, Springnight Carp, Guardfish, Silverfish and King Brocadefish. Only the gather is run-checked (Yukumo Hardwood, `0x2e0884` in WishFinder r139/r141).
- The centre popup's show sound is menu sound 5, heard as `sys_info` (tester, WishFinder r137/r138 runs), which is request 5 of `snd_sys_com` (Sound data); 30 is `sys_quest_papu`. A gather plays it and then, separately, the `item_gets` jingle. `cUIOInfoWindow`'s step `0x5b3d6c` (one caller, `0x5b3d2c` in the window's update `0x5b3d1c`) runs on state +0x4c. In state 1 it takes the head of the queued popups (+0x16c4, count +0x16c8) into +0x70, sets state 2 and builds the popup (`0x5b3fc4`). If the popup has lines (+0xc), it ends with `b 0x54f260(0, line 0 +0x24 == 1 ? 30 : 5)`, which reaches `0x4eeb78` with r1 5 and return address `0x5b3d30`. A queued popup plays it when it shows, not at the add. A gather in a quest adds through `0x19c320` (`0x19b7fc`, return `0x19c324`) and then requests an item line (`0x65de34` at `0x19c508`/`0x19c528`). In MHGU Recomp (WishFinder r137, `EVIDENCE.json` runtime_r137_recomp_2026_11_21) each such add was followed in the same update by that one call and no call of the other seven request functions it hooked (`0x4eef00` was not hooked), wishlisted or not. The `item_gets` jingle at a gather is the realtime jingle above, not `0x4eef00`, whose only callers are the BBQ Spit's end (r138 logged no `0x4eef00` call in a quest of gathers and supply box takes). Checked on one gather kind (Yukumo Hardwood); mining, bugs and carving were not run. A popup is up to six 56-byte lines from popup +0x18: +0x18 type, +0x1c flags, +0x20 message id, +0x24 and +0x28 arguments (type 3: +0x28 the item; `0x5b521c`), +0x2c a byte; popup +0x8 is the request id. A gather does not call the quest hunter's add-item `0x3015e0` (r39, r40: it adds through `0x19b7fc`), and the hunter's motion sound events do not depend on the item (r136: a wishlisted carve ran the same MSS events as unlisted ones). The realtime slots at +0x9ec change constantly; their +0xc is a running handle, not a sound number.

## Motion sound sequences (MSS)

Read from the 1.4.0 main (decompiled with the playbook's export, checked in `research dis`) and `sound\call\pl\pl_cmn` in `player/com/com.arc`. Decoder: `work/wishfinder/mss.py`.

- `rFestaSoundSequence` (DTI id `0x10ebe843`, vft `0x1769690`) is the `MSS` file: `sound\call\pl\pl_cmn` (player common, 330 motions) and `sound\call\pl\pl_wpNN` (one per weapon, in `player/quest/wNN.arc`). Its load (slot 0x2c, `0x4d9bec`) checks magic `0x53534d` and version `0x20131015`, copies the file to resource +0x64 and sets +0x68 = file + 0x10 and +0x6c = file + 0x410.
- File: +8 u16 record count, +0xb byte the file's type (`pl_cmn` 2), +0x10 512 u16 motion index (`0xffff` none), +0x410 records {u32 motion, u32 offset}. A sequence: +0 u32 motion, +4 u16 key count, +0xc offset of its start block, keys {u32, u32 offset} from +0x10 (`0x4d9e40`). A key: u16 frame, u16 event count, u32 event offsets from +4, each relative to the key (`0x4d9e68`). An event: u8 opcode, u8 kind (1 a sound command), u8 n, u8 flags (bit 0 skips it), then its arguments from +4 + n*4. Lookups: `0x4d9dbc(resource, motion)` (linear, on the sequence's own motion word), `0x4d9e20` the start block.
- `cFestaSoundSequence` (vft `0x17694d8`, 572 bytes) plays them for an owner at +0x164 with up to eight channels (count +8), one per motion layer: layer motion u16 at owner + 0x4b4 + layer*0x140 (high byte the bank), read as bank*1000 + index, and frame f32 at +0x500. Five resource slots at +0x150 (slot 4 for a motion 15000 and up). Per channel: +0x10 motion, +0x30 slot, +0xd0 key index, +0xf0 sequence, +0x130 key. The update is slot 0x18, `0x4d5e90`; it runs each key passed this frame through `0x4d65bc(sequence, channel)`, which calls the event executor for each event.
- Event executor `0x4d74f8(channel, sequence, event)` (callers `0x4d6624`, `0x4d6700`; entry `cmp r1,#0; cmpne r2,#0; beq`, no PC-relative loads). Argument readers: `0x4d7524`/`0x4d7538` u8, `0x4d754c` u16, `0x4d7560` s8, `0x4d7574` s16, `0x4d7588` u32. An opcode runs only when the file's type matches: 1 takes 0x40, 0x5e, 99; 2 takes 0x64..0x6a; 6 takes 0x79..0x7f, 0x82; 7 takes 0x80, 0x81, 0x84, 0x86; 0x83 and 0x85 check no type. Opcode 0x66 reads u16 bank, u16 request, s16 attach, u16, u8 random flag, u8 threshold, u16 alternative request, u8, and plays `0x4f0be8(system, owner, request, attach, u16, 4, bank)`. 0x64 and 0x6a also play through `0x4f0be8` with type 0, 0x65 type 1, 0x67 type 9, 0x68 type 5 (or `0x4f0700` when sequence +0x1aa is set). Every opcode takes the system from the same GOT cell (`0x1838be8`). In `pl_cmn`: 0x64 1071 events, 0x69 744, 0x68 540, 0x67 474, 0x65 151, 0x66 85.
- `0x4f0be8` has two direct callers, both in this code: the executor and `0x4d63b8`, the flush of the sequence's queued requests (+0x1ac, four of 0x20 bytes), which switches on owner byte +0x1052 (0, 6, 7 `0x4f0be8`; 1 `0x4f1974`; 2 `0x4f1c0c`; 4 `0x4f1ee4`).
- The Charge Blade to 4G mod blocks events with `opcode=0x66 / bank=0` by player, command and frame (`references/MHGU-Charge-Blade-To-4G/docs/Plugins.md`). Its playing a request through the player's sequence object (bank 0, attach 2) crashed the game (`docs/Presentation.md`), so a swap that changes the request on a copy of the event and runs the executor on it is preferred to a new call. Gather motions seen: 2005 and 2019 (common file), 202 (carve) and 206 (weapon file); the item-get sound is not among their events (Jingles, above).
