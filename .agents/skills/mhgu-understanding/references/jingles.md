# Jingles

## Jingles

- `sSoundControl` +0xc8 is `mpResSeJingle`. The pickup jingles are the realtime jingles, one per `arc/sound/rt_jNN.arc` (`sound\rt_j%02d`, built by `0x15339c`): 01 `item_non`, 02 `item_gets`, 03 `item_gets02`, 04 `katamari`, 05 `egg_get`, 06 `egg_lost`, 07 `mix`, 08 `fish_get`, 09 `trophy`, 10 `retire`. Stereo at 44.1 or 48 kHz.
- Three request functions queue a jingle in `sSoundControl`'s request slots (kind byte 2) on `mpResSeJingle`: `0x4eede8(sound, id, arg)` (one caller, the Alchemy barrel's result `0x2e115c` at `0x2e1340`: id = the barrel item index player +0x32e4 + 11, arg -2), `0x4eee68` (one caller, fixed id 1) and `0x4eef00(sound, kind)` (kind 0 -> id 2, 1 -> 3, 2/3/130/131 -> 4, 4 -> 5, else nothing). In a quest those ids are the quest jingle bank `<lang>\sound\se\jingle\quest\snd_jingle_qst` in `<lang>/arc/quest_<lang>.arc` (six waves; one group, keys 0..4 and 10): id 1 `normal_meet_bgm`, 2 `namaniku`, 3 `namayake`, 4 `jouzu`, 5 `koge`, 6 key 100 (no wave answers it), 11..15 `kizuna_success`. The `rt_jNN` names do not apply to these ids. The tester hears `jouzu` for a Well-done Steak (id 4). The village bank is `<lang>\sound\se\jingle\lobby\snd_jingle_lb` in `village/common_<lang>.arc`; which bank `mpResSeJingle` holds when is unread.
- **The gather jingle is a realtime jingle, `0x4ef090(sound, n)`** (`strb r1, [r0, #0xd5]; bx lr`, 13 callers). The hunter's get-item `0x2e04d4(player, item, ...)` adds through player slot 0x364 (the pouch add `0x19b7fc`, from `0x19c320`) and ends with `b 0x4ef090` with n 2 for a plain pickup (other branches below, "Which pickup gets which jingle"). The sound update's loader `0x4e9370` (state +0xd4) loads realtime jingle n (resource index 0x10414 + 532 + n, `0x1529a8`, then ready through `0x153078`) into +0xd0, keeps n at +0xd6, clears +0xd5, and queues request kind 3, id 1, bank +0xd0 inside the update, so the request table never shows it outside the update; the realtime slots do (`bank +0xd0`, word 1). In a run every gather of the run showed it two updates after its pouch add, and no supply box take did; the tester hears `item_gets` at a gather and `0x2e04d4`'s default n is 2, so n is the `rt_jNN` number (inference from that match, not heard for n 3). `sSoundControl` +0xd0 has no DTI name; +0xc0 `mpResSeSys`, +0xc4 `mpResSeSysLb`, +0xc8 `mpResSeJingle`, +0xd8 `mpResSeCom`, +0xdc `mpResSeMap`, +0xe0 `mpResSeTitle`, +0xe4 `mpResSeMonnyan`. Request slots: 64 of 36 bytes from +0xec (+0 used, +2 kind, +0x10 id, +0x14 word, +0x20 bank); realtime slots: 64 of 16 bytes from +0x9ec (+0 used, +4 resource, +8 request id, +0xc a handle, -2 when cleared; cleared at `0x4eb5fc`, walked at `0x4eb874`).
- `0x4eef00`'s callers (`0x2d55e0`, `0x2d5688`, `0x2d5734`, `0x2d5778`) are the end of the BBQ Spit (meat roasting), a switch on player +0x32d8, `| 0x80` for kind 2 when player byte +7 is clear. Each takes Raw Meat (45) through slot 0x360 and adds the result through slot 0x364. The kind comes from the roast timer f32 at +0x32d4 (`0x2d5488`), checked against the s16 table at `0x1628fb4` (360, 540, 40; the same row for item 44 and for the other spit): below 360 kind 0 (no item added, `namaniku`), 360 to 540 kind 1 Rare Steak (49, `namayake`), from 540 kind 2 Well-done Steak (50, `jouzu`), from 580 kind 4 Burnt Meat (51, `koge`). With skill 206 Outdoorsman ("Easier to fish and BBQ meat."), the well-done window is 530 to 590 (`vsel` at `0x2d541c`). Nothing in the function writes kind 3. The roast's start plays `0x4eee68` (id 1, `normal_meet_bgm`, the cooking tune; `0x2d5264`). So no BBQ result plays `item_gets02`.
- **Which pickup gets which jingle** (`0x2e04d4`, bytes). Arguments: player, item, amount, r3 flags (1 runs a quest check and `0x2e02d4`), stack word "fish" (0 from the gather wrapper, 1 from both fishing callers). Who calls it, and how gathering, mining, bugs, carving and fishing reach it: [Quest files](quest-files.md#gathering-areas-and-the-secret-area), "Pickups at runtime". Before the add, Honey (271), Royal Honey (2053) and the charms 353..356 can gain one: honey always with 244 Honey Hunter or 263 Soul of Yukumo; a charm on a roll below 30 of 100 with 245 Charm Chaser, 271 Crystalbeard Soul, 289 C.beard Soul X or 320 Pack Rat, else below 20 with 246 Charm Collector (skill ids: [Equipment box and equipped gear](equipment-box.md), skill effects). The add's result codes and popups are in [Items entering the pouch](pouch-and-equipment-screens.md#items-entering-the-pouch). Result 3 gives n 1 (`item_non`); on 5 the get-item queues hunter action 9999 (`0x2e9b7c(player, id, frames)`: the id at +0x2700, state +0x2754 = 3; ids from 1000 and from 2000 go through lookup tables, 9999 maps to 0) and plays n 1. Item 0 gives n 1 with no add. Otherwise, from the item record (`0x194228`; memory offsets, file layout in Equipment and crafting): a fish takes n 8 when +0xd (rarity, one below the shown value) is above 3, else 2; anything else takes n 4 when +0x1a is 2, else 2. After a successful add, an item in 2105..2115 (`0x1943bc`: the eggs, Sootstone, Quartz, Powderstone, Meteor Chunk, Eternal Fossil, Cannon Ammo) that the hunter now carries (`0x28813c`) sets the carry state and n 5. In 1.4.0's `table\itemData`, +0x1a is 2 only for Rustshard (357) and Ancient Shard (358). The fish with +0xd above 3 are Speartuna, Gastronome Tuna, Ancient Fish, Armored Bream, Springnight Carp, Guardfish, Silverfish and King Brocadefish. Only the gather is run-checked (Yukumo Hardwood, `0x2e0884`).
- The centre popup's show sound is menu sound 5, heard as `sys_info` (tester), which is request 5 of `snd_sys_com` (Sound data); 30 is `sys_quest_papu`. A gather plays it and then, separately, the `item_gets` jingle. `cUIOInfoWindow`'s step `0x5b3d6c` (one caller, `0x5b3d2c` in the window's update `0x5b3d1c`) runs on state +0x4c. In state 1 it takes the head of the queued popups (+0x16c4, count +0x16c8) into +0x70, sets state 2 and builds the popup (`0x5b3fc4`). If the popup has lines (+0xc), it ends with `b 0x54f260(0, line 0 +0x24 == 1 ? 30 : 5)`, which reaches `0x4eeb78` with r1 5 and return address `0x5b3d30`. A queued popup plays it when it shows, not at the add. A gather in a quest adds through `0x19c320` (`0x19b7fc`, return `0x19c324`) and then requests an item line (`0x65de34` at `0x19c508`/`0x19c528`). In a run each such add was followed in the same update by that one call and no call of the other seven request functions (`0x4eef00` not observed). The `item_gets` jingle at a gather is the realtime jingle above, not `0x4eef00`, whose only callers are the BBQ Spit's end (a run logged no `0x4eef00` call in a quest of gathers and supply box takes). Checked on one gather kind (Yukumo Hardwood); mining, bugs and carving were not run. A popup is up to six 56-byte lines from popup +0x18: +0x18 type, +0x1c flags, +0x20 message id, +0x24 and +0x28 arguments (type 3: +0x28 the item; `0x5b521c`), +0x2c a byte; popup +0x8 is the request id. A gather does not call the quest hunter's add-item `0x3015e0` (run: it adds through `0x19b7fc`), and the hunter's motion sound events do not depend on the item (run: carves of different items ran the same MSS events). The realtime slots at +0x9ec change constantly; their +0xc is a running handle, not a sound number.
